# Harness v1 Phase 1 contract

Issue: #206

Contract version: `harness-v1-phase1/1`

Date: 2026-08-29

This document freezes the canonical types, state invariants and acceptance fixtures for the first implementation slice. Exact Python class layout and SQL column naming may vary, but implementation must preserve these semantics without breaking changes.

Phase 1 is a **single-process durable direct-provider core**. It is deliberately not multi-worker recovery, compaction, parallel mutation, subagents or full external-harness recovery.

## 1. Phase 1 compatibility target

The first production path is current OpenAI-compatible/LM Studio inference behind the new canonical contracts. Current Cerebro product behavior remains the acceptance baseline.

Current seams to bridge, not rewrite from scratch:

- `cerebro/runtime.py::AgentRuntime.run_turn/_generate/_run_tool`
- `cerebro/context.py::ContextBuilder.build`
- `cerebro/providers/base.py::Provider.stream(list[Message], ...)`
- `cerebro/providers/openai_compatible.py::OpenAICompatibleProvider` / `to_chat_messages`
- `cerebro/providers/lmstudio.py::LMStudioProvider`
- `cerebro/providers/cli_agent.py::CliAgentProvider`
- `cerebro/service.py::RuntimeService`, `_provider_for`, tool/profile composition
- `cerebro/poller.py::ChannelPoller`
- `cerebro/tools.py::CoreTools`
- `cerebro/mcp.py::MCPRegistry` / `CompositeToolExecutor`
- `cerebro/turnguard.py::TurnGuard`
- `cerebro/db.py::run_in_writer`
- `cerebro/persistence.py::StoreAdapter`
- `cerebro/hub.py::Hub`
- `budget_usage` versus `agent_quota`

Phase 1 adds Harness state beside existing collaboration state. It does not redefine `messages`, product `tasks`, current `tool_calls`, or current `audit_events`.

## 3. `CausalWakeKey`

One semantic wake for one agent must admit one durable `AgentTurn`.

Current message-driven key semantics:

```text
CausalWakeKey
  wake_kind: direct_message | channel_poll | explicit_turn | future_kind
  target_agent_id
  channel_id
  trigger_message_id?
  occurrence_id?          # required for intentionally recurring wakes
```

The serialized key or a stable hash has a uniqueness constraint in the Harness turn-admission store.

A duplicate delivery returns/loads the existing `AgentTurn`; it does not create another execution.

Phase 1 does not make `ChannelPoller` delivery itself restart-durable. It only ensures duplicate causal admission converges if the same wake reaches the harness.

## 11. `InferenceAttempt`

Every provider request has durable identity before dispatch.

```text
InferenceAttempt
  attempt_id: InferenceAttemptId
  agent_turn_id
  step_snapshot_id
  attempt_generation: int
  turn_version_admitted

  dispatch_state: ProviderDispatchState
  semantic_state: ProviderAttemptSemanticState

  request_semantic_hash
  provider_request_id?
  error?
  completion_status?
  started_at?
  completed_at?
```

```text
ProviderDispatchState =
  admitted
  dispatch_may_have_escaped
  terminal

ProviderAttemptSemanticState =
  active
  completed
  failed
  abandoned
  cancelled_before_dispatch
```

Dispatch rule:

1. persist attempt as `admitted` bound to snapshot;
2. before network call can begin, durably mark/admit `dispatch_may_have_escaped`;
3. then invoke adapter.

This conservative barrier permits false uncertainty after a crash before bytes actually leave the process, but never the unsafe inference that missing local completion means the provider was not called.

Late events may affect current turn semantics only if their attempt is still the active admitted attempt for the expected snapshot/turn version.

## 15. Tool recovery capability

```text
ToolRecoveryCapability
  effect_class: read_only | side_effecting
  repeat_semantics:
    idempotent
    stable_idempotency_key
    reconcile_before_repeat
    never_automatic_repeat
  reconciliation_binding?
  operation_key_policy?
```

Rules:

- read-only calls may be repeated only if the executor says the operation truly has no externally relevant side effect;
- `idempotent` means identical canonical operation can be safely repeated;
- `stable_idempotency_key` requires reusing the same durable operation key across retry;
- `reconcile_before_repeat` requires authoritative lookup before deciding whether another dispatch is allowed;
- `never_automatic_repeat` resolves/suspends as indeterminate after dispatch uncertainty.

A static `parallel_safe` flag is not a recovery guarantee.

## 16. `ToolExecution`

Every admitted `CerebroCallId` has one durable monotonic execution record.

```text
ToolExecution
  call_id: CerebroCallId
  agent_turn_id
  step_snapshot_id
  tool_call_item_id
  tool_key
  admitted_turn_version

  dispatch_state: ToolDispatchState
  resolution: ToolResolution?

  binding_generation
  recovery_capability
  stable_operation_key?

  raw_output_ref?
  model_output_item_id?

  admitted_at
  dispatch_marked_at?
  resolved_at?
```

```text
ToolDispatchState =
  not_dispatched
  dispatch_may_have_escaped
  resolved

ToolResolution =
  known(status: ToolResultStatus)
  indeterminate_needs_attention
```

Monotonicity:

- `not_dispatched > dispatch_may_have_escaped > resolved`
- pre-dispatch denial/cancellation/unavailability may move `not_dispatched > resolved` directly;
- no transition moves backward;
- once resolved, later timeout/cancellation cannot overwrite it;
- `indeterminate_needs_attention` is a truthful terminal harness resolution when effect truth cannot be recovered.

## 17. Pre-side-effect checkpoint transaction

A side-effecting tool is not executable until this durable set is committed:

```text
A. immutable StepSnapshot exists
B. active InferenceAttempt identity exists
C. all finalized preceding OutputItemCompleted items are persisted in order
D. completed ToolCallItem is persisted
E. CerebroCallId is assigned/persisted
F. replay-required ProviderCallRef is persisted
G. all preceding required ProviderOpaqueItems are persisted
H. inference_history_version/provider_replay_version advance consistently
I. ToolExecution exists in not_dispatched state
J. ToolExecution binds exact ToolBinding generation/recovery capability
K. AgentTurn state_version advances to the executable-call checkpoint
L. matching sparse turn event/checkpoint is committed consistently
```

The transaction uses current SQLite writer discipline (`db.run_in_writer()` / `BEGIN IMMEDIATE` or an equivalent helper built on it).

Only after commit may a later transaction mark `dispatch_may_have_escaped`; only after that mark commits may the external executor be invoked.

## 18. Tool result commit

When an authoritative known executor result is available:

1. normalize/store full raw output or durable artifact reference;
2. generate bounded explicit model-visible projection;
3. create exactly one `ToolResultItem` for the canonical call;
4. transition `ToolExecution > resolved/known`;
5. append result item and advance history version;
6. advance `AgentTurn.state_version`;
7. commit matching sparse event/checkpoint consistently;
8. only then admit the next provider step.

If the executor outcome is unknown after dispatch:

- run reconciliation/idempotent recovery only as declared by the frozen binding;
- otherwise resolve `indeterminate_needs_attention`, append a truthful `ToolResultItem(status=indeterminate)` if/when the turn is made resumable with that evidence, and suspend/fail according to policy;
- never issue a blind second mutation.

## 19. Cancellation contract

Turn cancellation is represented separately from provider/tool outcomes.

Rules:

- before provider/tool dispatch is admitted, cancellation may prevent dispatch and produce `cancelled_before_dispatch` where applicable;
- after dispatch may have escaped, cancellation stops waiting/future autonomous work but does not prove failure/no-effect;
- a durably known tool success remains success;
- an unresolved dispatched effect remains unknown unless executor cancellation/reconciliation proves otherwise;
- after terminal turn cancellation, no new provider attempt or tool dispatch may be admitted;
- late provider/tool completions may be stored as diagnostic/stale evidence but cannot restart autonomous work or overwrite current resolution.

Current Phase 0 Hub activity/cancelled events and CLI child termination remain required projections/cleanup.

## 20. Provider/model switch contract

Switching to a provider/model whose adapter cannot consume active required replay state is a semantic boundary.

Required sequence:

1. mark old active attempt/continuation `abandoned` durably;
2. retain its provider-opaque state only in its owning replay/audit scope;
3. build new StepSnapshot from portable semantic items only;
4. start a new `InferenceAttemptId`;
5. reject/fence late old-attempt `OutputItemCompleted`/completion from current history/tool admission.

No adapter translates opaque reasoning/signature material to another provider family.

## 22. CompletionPolicy contract

```text
CompletionDecision =
  allow(ProductOutcome)
  continue_with_feedback(list[InferenceItem])
  fail(reason)
  suspend(reason)
```

Phase 1 implementation preserves current chat semantics exactly:

- topic exact PASS > `allow(topic_pass)` with zero final agent rows;
- topic empty `Done(stop)` > `allow(topic_silent_stop)` with zero final agent rows;
- DM PASS > `allow(fail_closed_error)` with current error message;
- DM empty stop > `allow(fail_closed_error)` with current error message;
- ordinary accepted text > `allow(final_message)`;
- unserviced pending tool calls/provider failure retain current fail-closed visible behavior unless separately approved.

Provider `InferenceCompleted(end_turn)` does not bypass this policy.

## 23. Finalization transaction

For ordinary final output or fail-closed error, one idempotent SQLite transaction commits:

```text
insert exactly one final collaboration messages row
  + set AgentTurn.product_outcome_kind
  + set AgentTurn.final_message_id
  + set terminal AgentTurn.lifecycle/state_version/completed_at
  + record matching durable finalization event/checkpoint
```

For topic PASS/silent completion, one transaction commits the terminal turn/product outcome and intentionally no final agent message.

Transient `message.new` / `message.done` / `turn.discarded` Hub events are emitted after durable commit and may be duplicated/lost without changing recovery truth.

Completion-ordered final message behavior remains the database commit/insertion order behavior characterized in Phase 0.

## 24. Durable storage semantic contract

Phase 1 introduces new Harness-owned storage. Recommended semantic tables/collections:


Implementation may combine some immutable payloads into versioned JSON blobs if atomicity/queryability remain sufficient. It must not combine away the identities/state transitions required by this contract.

### Explicit non-reuse decisions

- `messages`: collaboration/product transcript only; final public results remain here.
- `Message.meta_json`: product/import compatibility metadata; not canonical replay state.
- existing `tool_calls`: leave untouched in Phase 1 rather than silently assigning new recovery semantics.
- existing `audit_events`: leave untouched rather than claiming it is `turn_events`.
- product `tasks`: do not overload with reducer/effect semantics.

## 26. Hub and telemetry contract

Hub remains transient and lossy by design.

Phase 1 preserves current event envelopes where externally observable. Durable Harness facts may generate additional internal/UI events later, but Hub sequence numbers are never restart/recovery identity.

Usage rules:

- provider `UsageUpdate` continues publishing live usage and writing `budget_usage` best effort;
- usage persistence failure remains non-fatal while usage is telemetry;
- zero-token usage remains ignorable as today;
- `agent_quota` remains external-harness self-reporting and is not merged with measured provider token usage;
- if a later hard budget uses spend for admission, it requires a new durable reservation contract before provider dispatch.

## 28. New deterministic Phase 1 acceptance fixtures

These fixtures are mandatory before the direct-provider reducer path is considered complete.

### F-01 — canonical message projection

Given current workspace/channel `Message` history, projection produces ordered canonical instructions/items with identical current agent/peer authorship semantics. No provider-specific tool protocol is required in collaboration `meta_json`.

### F-02 — OpenAI-compatible compatibility round trip

Canonical `MessageItem`/`ToolCallItem`/`ToolResultItem` serialize through the compatibility adapter to the exact valid chat-completions assistant/tool sequence expected by current LM Studio/OpenAI-compatible tests.

### F-03 — provider attempt durable before dispatch

Fake adapter exposes a barrier immediately before request send. Database already contains `InferenceAttemptId` bound to the immutable snapshot. Kill/restart leaves an explicit admitted/dispatch-uncertain attempt rather than "no call happened."

### F-04 — deltas are never executable authority

Fake provider emits a tool name and complete-looking JSON arguments, then delays native call ref/required opaque signature. Tool invocation count remains zero until `OutputItemCompleted` and full replay checkpoint commit.

### F-05 — replay checkpoint crash matrix

Inject process failure after each of A-K in section 17. Any durable state before the full executable checkpoint yields zero external tool calls. Once executable, recovery has one stable `CerebroCallId` and snapshot/replay set.

### F-06 — non-idempotent ambiguity

Fake remote tool commits one mutation, then loses response before local result commit. Restart observes `dispatch_may_have_escaped`; automatic second invocation count is zero; call becomes reconciled or `indeterminate_needs_attention` according to declared capability.

### F-07 — stable idempotency key retry

Fake executor requires an idempotency key, records one mutation, loses first response, then accepts retry with the same key. Harness records one remote mutation and one canonical call resolution.

### F-08 — known result is monotonic

ToolResult success is durably committed. Next provider step fails transiently. Restart/fresh attempt includes the committed result and never re-executes the call or rewinds to pre-tool history.

### F-09 — cancellation race matrix

Deterministic barriers cancel:

- before tool dispatch mark;
- after dispatch mark but before executor call;
- after external success before result persistence;
- after result persistence;
- before next provider-step admission.

Live and restarted durable truth match. Known success is never rewritten as cancelled; uncertain external effect is never fabricated as failure.

### F-10 — stale/superseded provider attempt

Attempt A is abandoned; attempt B becomes active and commits output. Deliver late `OutputItemCompleted(tool call)` and `InferenceCompleted` from A. Current history does not change and tool invocation count remains zero.

### F-11 — provider/model replay boundary

Create required provider-opaque item for provider A, abandon/switch to incompatible provider B. B request contains portable semantic history but no A opaque payload. Late A output is non-authoritative.

### F-12 — optional continuation/cache loss

For an adapter/profile advertising `stateless_lossless_replay=true`, remove optional continuation/cache handles before next request. Adapter reconstructs provider-valid request from durable canonical history plus required replay items/refs.

### F-13 — raw/model tool-output split

Fake tool returns a very large result. Durable raw output remains complete/identifiable; model-facing `ToolResultItem.content` is bounded with explicit omission metadata. Hub output may be separately bounded without destroying raw evidence.

### F-14 — stale tool binding generation

Build snapshot with binding generation G1. Replace same-named MCP/tool binding with G2 while provider streams. Call from old snapshot invokes G1 if still addressable or resolves stale/unavailable; invocation count on G2 is zero.

### F-15 — security revocation

Snapshot grants a side-effecting tool. Advance security revocation epoch before dispatch. Old call resolves denied/stale under original identity and is never rebound to a new grant.

### F-16 — sequential multiple calls

Provider finalizes multiple calls in one step. ToolRuntime executes in deterministic original order, not parallel, and each call has independent durable execution state/result.

### F-17 — finalization crash matrix

Inject failure around each statement of product finalization and restart repeatedly. Outcome is exactly one of:

- one ordinary final row + terminal turn;
- zero row + explicit topic PASS/silent terminal outcome;
- one fail-closed DM error row + terminal turn.

Never duplicate or silently lose the product outcome.

### F-18 — Hub events are not recovery truth

Drop/duplicate Hub events around durable commits. Database/Harness reconstruction remains correct; clients can resync from durable product state.

### F-19 — usage persistence remains non-fatal

Force `budget_usage` write failure after successful inference. Turn continues/finalizes according to current behavior; failure does not alter canonical execution truth.

### F-20 — provider concurrency remains capacity-only

Run overlapping fake requests for provider A and B. Existing per-provider isolation remains observable. Resetting a process-local semaphore in a restart fixture does not allow duplicate durable effect admission.

## 32. Issue #210 contract clarifications — normative addendum

This section applies the accepted AR-01 through AR-12 findings from issue #209 at
`review/harness-v1-architecture-audit@46865080a74a20f7406df506d7c6668ffdafc283`.
It is normative for implementation and supersedes earlier wording in this document only where the
older text is less specific. It does not reopen or reverse any frozen issue #206 architecture
decision.

### 32.1 Canonical persisted type deltas — AR-02 and AR-10

The following fields are part of the canonical persisted contracts from PR 1 onward:

```text
InferenceItem shared persisted envelope
  item_id: InferenceItemId
  format_version: int
  producing_attempt_id: InferenceAttemptId?

InferenceAttempt
  format_version: int
  ... existing fields from section 11 ...

ToolExecution
  format_version: int
  ... existing fields from section 16 ...
```

`producing_attempt_id` is present on every persisted `InferenceItem`. It is required and non-null for
provider-originated items emitted through `OutputItemCompleted`; it is null only for items projected
from non-provider product/context state or otherwise created outside a provider attempt. Provider
adapters may not substitute generic provenance for this identity.

Every persisted row/object in these three families carries its own `format_version`; schema epoch or
event-envelope versioning is not a substitute.

### 32.2 Interrupted/superseded attempt item disposition — AR-02

When an `InferenceAttempt` is abandoned without authoritative `InferenceCompleted`, finalized items
already persisted from that attempt are not all treated alike:

- Provider-originated items that authorized no tool/provider side effect which reached
  `dispatch_may_have_escaped` are attempt-scoped. On abandonment they are durably marked
  superseded, retained as audit evidence, and excluded from every later `InferenceRequest.history`.
- If a dispatched or committed side effect exists, the smallest ordered prefix needed to preserve
  the causal history of that effect, plus every committed tool resolution/result, remains active
  canonical semantic history. It is never superseded merely to retry the provider.
- Trailing finalized output after the last protected effect boundary may be superseded when it did
  not authorize another dispatched effect.
- Supersession is durable metadata on the inference-item storage envelope (`superseded_at`, reason,
  and superseding/new-attempt identity where applicable); it is never implemented by deleting audit
  evidence.

This refines the monotonic-progress rule: Cerebro never rewinds across committed/possibly escaped
external effects, while an incomplete provider attempt cannot accidentally become an assistant
prefill in the next semantic retry.

### 32.3 Restart recovery driver and suspension — AR-01

The Phase 1 restart driver is **`TurnRecoveryDriver`**, a logical responsibility owned by
`TurnCoordinator`. At process startup, before admitting new wakes for an agent,
`TurnRecoveryDriver` scans all non-terminal `agent_turns` in the active `execution_epoch`.
`queued`/`running` rows are driven through the section 12/18/19 recovery rules; already `suspended`
rows remain suspended unless an explicit resume disposition exists.

Every scanned turn must reach one of: safely resumed `running`, terminal, or durably `suspended`.
A turn that Phase 1 cannot safely reconstruct/resume, including a non-recoverable external-agent
execution, is transitioned to `suspended` with an explicit `suspension_reason`; it may not remain
`running` indefinitely because the prior process disappeared.

### 32.4 Conversation-retained replay storage ownership — AR-03

`inference_items` uses a conversation-scoped durable owner from its first schema. For current Phase 1
product paths the owner is the stable Cerebro conversation/channel identity already used to build
history. Every item row also carries required `agent_turn_id` attribution and its ordered sequence
metadata. Turn-scoped reads are filters over this conversation-owned collection, not a different
primary ownership model.

`ReplayRetentionScope.conversation` therefore retains required replay items across later turns
without re-keying the central `inference_items` model. Provider replay state remains separate from
collaboration `messages`/`Message.meta_json`.

### 32.5 Causal wake uniqueness and occurrence semantics — AR-07

The Phase 1 serialized key is versioned and derived from these tuples:

```text
direct_message = (direct_message, target_agent_id, channel_id, trigger_message_id)
channel_poll   = (channel_poll, target_agent_id, channel_id, trigger_message_id)
explicit_turn  = (explicit_turn, target_agent_id, channel_id, occurrence_id)
```

For a message-driven DM/poll, `trigger_message_id` is the occurrence identity. A poll wake without a
durable trigger message and every explicit/manual turn must supply a durable `occurrence_id` from
the wake layer. Future intentionally recurring wake kinds likewise require explicit occurrence
identity.

A duplicate key loads the existing turn only while that row is the same admitted occurrence and is
non-terminal/recoverable. Re-delivery of the same occurrence after terminal completion returns the
recorded terminal/decline outcome and never silently starts a second execution. A legitimate later
occurrence must carry a distinct occurrence identity and therefore a distinct key; a terminal prior
wake cannot permanently suppress it. If the product declines a new occurrence, that decline is a
durable recorded decision rather than a silent uniqueness-conflict drop.

### 32.6 Pre-tool checkpoint atomicity and stable operation key — AR-06

Section 17's list A-L is a required **checkpoint/precondition set**, not twelve separately durable
mini-transactions. Add:

```text
E2. when the frozen ToolBinding declares stable_idempotency_key,
    stable_operation_key is assigned and persisted before dispatch eligibility
```

The atomic barrier transaction commits D, E, E2 (when applicable), I, J, K and L together. A, B, C,
F, G and H may have been committed by earlier authoritative streaming/snapshot transactions, but the
barrier transaction must verify them against the expected snapshot/attempt/history/replay versions
and fail closed if any is missing or stale. No external executor invocation is possible unless the
entire set is true after the atomic barrier commit.

`stable_operation_key` is then reused unchanged for every executor retry whose recovery capability
requires stable externally enforced idempotency.

### 32.7 One execution authority per causal wake — AR-08

For one admitted `CausalWakeKey`, exactly one execution authority may dispatch a provider, dispatch a
client tool, or insert a collaboration/product result row. Legacy/compatibility/shadow paths may
observe the same wake only when they are mechanically non-side-effecting for it. A feature flag or
shadow comparison is not permission for dual execution.

This is a frozen safety invariant, not an implementation-review question.

### 32.8 Outstanding indeterminate execution ownership and visibility — AR-04

`AgentTurn` has an authoritative durable projection of outstanding uncertain effects:

```text
AgentTurn
  needs_attention: bool
  unresolved_effect_count: int
```

These fields are maintained in the same SQLite transaction as relevant `ToolExecution` transitions.
Any execution at `dispatch_may_have_escaped` without a known/reconciled outcome contributes to the
count; resolving it removes that contribution. Cancellation/failure/other turn termination never
implicitly resolves or hides the execution. A terminal turn with an outstanding uncertain effect
remains `needs_attention=true` until authoritative reconciliation resolves it.

Minimum Phase 1 discovery surface: `TurnStore` must support querying/listing turns needing attention
and reading the associated unresolved `CerebroCallId`, `ToolKey`, dispatch state and reason without
requiring replay of transient Hub events. The product/operator layer must expose a durable status
projection derived from that store; Hub may mirror it but is not the sole notification channel.
Sensitive provider payloads/raw tool output are not required on this surface.

### 32.9 Product finalization discriminator — AR-05

`AgentTurn.product_outcome_kind` is the authoritative idempotency/finalization discriminator. A
re-entered finalization path checks this field first and either validates/returns the existing
outcome or performs the one finalization transaction when it is absent.

`final_message_id` is evidence associated with `final_message`/`fail_closed_error`; it is never, by
itself, a finalization predicate. Its intentional absence for `topic_pass` and `topic_silent_stop`
must not cause finalization to run again.

Any user-visible error/failure publication participates in the same atomic finalization semantics:
the message insert (when any), `product_outcome_kind`, `final_message_id` (when any), terminal
lifecycle/state version, and durable finalization event commit together.

### 32.10 Corrected and added acceptance fixtures — AR-09

The following definitions replace the earlier F-05, F-07 and F-14 text:

**F-05 — replay checkpoint crash matrix.** Inject process failure at the defined durable boundaries:
pre-barrier, immediately after the atomic barrier commit, after `dispatch_may_have_escaped` commits,
after executor invocation before result commit, and immediately after result commit. Assert the
D/E/E2/I/J/K/L atomic set is all-or-nothing; every pre-barrier state yields zero external calls; and
recovery after an executable boundary retains exactly one `CerebroCallId`, snapshot/replay set and
operation key where applicable.

**F-07 — stable idempotency key retry across restart.** A fake executor requires an idempotency key,
records one mutation and loses the first response. Kill the process after the durable dispatch mark
and before retry. After restart, recovery reuses the exact durably persisted
`stable_operation_key`; the fake remote records exactly one mutation and the Harness records one
canonical call resolution.

**F-14 — stale tool binding generation, deterministic arms.** Arm A keeps frozen generation G1
addressable while replacing the live same-named binding with G2; the old snapshot must invoke G1 and
G2 invocation count is zero. Arm B makes G1 unaddressable before dispatch; the old snapshot must
resolve stale/unavailable under the original call identity and G2 invocation count is zero. A test
must select one setup and assert its single expected outcome rather than accept either result.

Add these mandatory fixtures:

**F-21 — causal admission.** Duplicate delivery of one occurrence produces one `AgentTurn` and one
execution authority. Re-delivery matching a terminal turn returns a defined recorded terminal/decline
outcome rather than silently disappearing. A legitimate later occurrence with a new occurrence
identity is admitted. A wake matching a crash-orphaned non-terminal turn drives recovery rather than
being permanently wedged by uniqueness.

**F-22 — rollout single authority.** Load legacy/compatibility and durable-reducer paths together for
one causal wake. Assert at most one provider dispatch, at most one tool dispatch per logical call,
and exactly one collaboration product row; every shadow path is non-side-effecting.

**F-23 — orphaned in-flight attempt recovery.** Restart with an attempt at
`dispatch_may_have_escaped` holding finalized partial output. Recovery reaches a defined resumed,
terminal or suspended turn state; unprotected partial assistant output is superseded and absent from
the next request; protected committed-effect history remains monotonic; superseded rows remain as
audit evidence.

**F-24 — indeterminate visibility.** Cancel while a `never_automatic_repeat` tool is at
`dispatch_may_have_escaped`. Assert no second dispatch, no fabricated known status, and after restart
a durable readable turn-level attention projection points to the unresolved execution.

The applicable deterministic Phase 1 acceptance set is now **F-01 through F-24**. Phase 1D / PR 5
may not claim the crash/recovery exit bar with only F-01 through F-20 green.

### 32.11 Provider continuation admission — AR-11

Phase 1 admits a `ProviderAdapter` + `ModelProfile` combination only when every continuation datum
required for correctness can be represented losslessly in durable ordered `InferenceItem` /
`ProviderOpaqueItem` / `ProviderCallRef` state and reconstructed into a provider-valid next request.
Adapters must validate this before use.

If required continuation cannot be safely reconstructed, generic Harness code does not invent a
replay strategy. For provider attempts, `reconcile_or_suspend` has no generic provider-side
reconcile operation in Phase 1 and therefore degenerates to durable `suspend` unless the specific
adapter contract later supplies authoritative reconciliation.

### 32.12 Security/storage gates tied to the creating PR — AR-12

Sensitive replay material: PR 1 must state whether the OpenAI-compatible/LM Studio adapter can emit
`hidden_reasoning`, `signature_or_encrypted_reasoning`, or `secret_like` replay payloads. Before the
first adapter PR that can persist any such payload, that same PR must define and review at-rest
classification, access, encryption where required, retention/deletion and log/redaction behavior.
No sensitive replay material may be durably created first and governed later.

Raw tool output: PR 3 must define inline-size threshold, artifact/blob ownership, retention/deletion,
access and redaction/failure behavior **before** PR 3 persists raw tool output or lands F-13. The
policy gate cannot be deferred past the PR that creates the data.

### 32.13 Standing external-side-effect rule remains unchanged

Nothing above weakens frozen decision 18. Cerebro does not promise generic exactly-once external
side effects. A call whose effect may have escaped is not automatically repeated unless executor
semantics prove read-only behavior, idempotency, stable externally enforced idempotency, or
authoritative reconciliation.
