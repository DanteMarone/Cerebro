# Current Cerebro seams mapped to Harness v1

Issue: #207

Source baseline: `main@57e9c4ecd8b470145afc51c2c1f6771a2f560fd7`

This is an implementation inventory, not a Harness v1 architecture decision. “Likely seam” below means the narrowest current boundary that #206 can evaluate; it does not prescribe the final design.

## Summary

Current Cerebro has useful seams, but they are organized around a collaboration message runtime rather than a durable, re-entrant inference harness. The central concentration point is `cerebro/runtime.py::AgentRuntime`: it coordinates provider inference, provider-specific tool protocol history, tool execution, completion policy, usage, event publication, concurrency and persistence. `cerebro/service.py::RuntimeService` sits above it and owns wake/dispatch plus cancellation of live tasks.

The largest Phase 1 migration pressure is the fact that the provider contract accepts `list[Message]`. `Message` is also the SQLite/channel model. Tool protocol information is therefore encoded in `Message.meta_json`, and `OpenAICompatibleProvider.to_chat_messages()` reconstructs OpenAI chat-completions turns from that JSON. In the live tool loop those protocol-only messages are synthetic in-memory `Message` objects and are not durably appended to the channel transcript at all.

## Current call graph

Immediate DM path:

`POST /api/channels/{id}/messages` or WebSocket `message.send` > `store.append_message` > `Hub.publish("message.new")` > `RuntimeService._run` > `_consider` > `_responder` > `asyncio.create_task(AgentRuntime.run_turn)`.

Polling path:

`RuntimeService.poller` > `ChannelPoller.tick/_consider` > SQLite latest message id comparison > `RuntimeService._poll_turn` > `AgentRuntime.run_turn`.

Turn path:

`AgentRuntime.run_turn` > `TurnGuard.check` > `_provider_for(agent)` > `_context` / `ContextBuilder.build` > provider semaphore > `_generate` > `Provider.stream` > optional `_run_tool` / `CompositeToolExecutor.execute` > repeated provider call > completion policy > `StoreAdapter.append_message` > Hub final events.

## OpenAI-chat-shaped assumptions to preserve explicitly during migration

1. `Provider.stream()` accepts `list[Message]`, so the collaboration data model doubles as inference history.
2. `OpenAICompatibleProvider._role_for()` maps only the current agent’s own messages to `assistant`; every peer agent becomes a `user` turn prefixed with `<agent_id>:`.
3. `ContextBuilder.build()` emits exactly one `system` `Message` because consecutive system-role messages failed against a local chat template. This is a compatibility workaround for chat-template behavior, not provider-neutral history semantics.
4. Tool definitions are OpenAI-function shaped by `_tools_payload()` (`type=function`, nested `function`, JSON Schema parameters).
5. `AgentRuntime._generate()` creates OpenAI-style assistant `tool_calls` and tool result `tool_call_id` payloads inside `Message.meta_json`.
6. `OpenAICompatibleProvider.to_chat_messages()` knows those exact `meta_json` keys and restores the required assistant/tool sequence.
7. Live tool-call/result protocol messages created in `_generate()` are not durably appended to `messages`, so a process restart between side-effect execution and the next provider call cannot reconstruct that tool round from SQLite.
8. `Params` exposes chat-completions-era `temperature`, `max_tokens`, `stop`; provider-native controls/replay identifiers have no first-class home.

## Other coupling notes

- `CoreTools` is constructed in `service.py` without a Hub. Its `post_message` implementation publishes `message.new` only when `self._hub` exists, so the service-owned core tool path persists a message without publishing that live wake/UI event. This is current behavior worth characterizing before migration; it should not be silently “fixed” by #207.
- `MCPServerConfig` contains `trust` and `env`, but `StdioMCPClient.start()` does not pass `config.env` to the subprocess and `MCPRegistry.filter_specs_for_agent()` filters by the agent profile’s `tools_enabled` globs rather than server trust. These fields should not be mistaken for fully enforced permission boundaries.
- The `tool_calls` table and `ToolCall` Pydantic model are not used by `AgentRuntime._run_tool`; current tool execution durability is therefore weaker than the schema’s presence suggests.
- `AgentRateLimiter` is covered by `tests/test_turnguard.py`, but no use from `AgentRuntime`, `RuntimeService` or `ChannelPoller` was found in the current source paths inspected for #207.
